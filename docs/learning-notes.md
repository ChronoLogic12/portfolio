# Learning notes

Concepts covered while building this site, and where to find them in the code. Newest at the bottom.

## 1. TanStack Start and static prerendering (16 Oct 2026)

**What TanStack Start is.** TanStack Router plus a build and server layer. The Router part is the same as in grid tracker: file-based routes, typed links, `head` per route. Start adds server-side rendering (SSR): React can render a page to HTML on a server, and then the browser "hydrates" that HTML, meaning React attaches to the existing markup instead of building the page from scratch.

**Why we want it.** A plain Vite single-page app ships one empty `index.html` and builds everything in the browser. That's fine for a dashboard, but link previews (LinkedIn, Slack) and search engines read the raw HTML, so every page would look the same to them. With Start, each page's HTML already contains its content and its own `<title>` and meta tags.

**Why there's still no server.** Prerendering runs the SSR step _once, at build time_, for every page it can find, and saves the results as files. At runtime it's just static files on S3 behind CloudFront, the same as grid tracker.

### The files

| File                                     | Role                                                                                                                                                                                                                                                              |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `site/vite.config.ts`                    | Adds the `tanstackStart()` Vite plugin (must come before the React plugin) and turns on `prerender`                                                                                                                                                               |
| `site/src/router.tsx`                    | `getRouter()` creates the router from the generated route tree. Start calls it, once per page render at build time and once in the browser                                                                                                                        |
| `site/src/routes/__root.tsx`             | The root route. Unlike a Vite SPA there's no `index.html`: this component renders the whole document, `<html>`, `<head>` and `<body>`. `<HeadContent />` outputs the merged `head()` meta of the matched routes; `<Scripts />` adds the JS that hydrates the page |
| `site/src/routes/index.tsx`, `about.tsx` | One file per page. `createFileRoute('/about')` defines the route; a route's `head()` overrides the root's title                                                                                                                                                   |
| `site/src/routeTree.gen.ts`              | Generated by the Router plugin from the `routes/` folder whenever dev or build runs. Never edit it. It's what makes `<Link to="/about">` type-checked                                                                                                             |

### What `npm run build` does

1. Builds the **client** bundle into `site/dist/client/assets/`: the JS the browser downloads
2. Builds the **server** bundle into `site/dist/server/`: the same app compiled to render HTML in Node
3. **Prerenders.** Starts that server bundle, requests `/`, saves the HTML, and because `crawlLinks` is on, follows every link it finds (`/about`) and saves those too. Each page lands at `<path>/index.html` so `/about` works as a plain file path

Only `site/dist/client/` is deployed. `dist/server/` exists only so the build can do step 3.

`failOnError: true` makes the build fail if any page throws while rendering, so a broken page can't be deployed.

### Checked

Served `site/dist/client` with a plain static file server (no Node app). The home page loaded, clicking About changed the URL and title without a full page reload (the client router took over after hydration), and the console had no errors.

### Things to know

- Routes with parameters (e.g. `/projects/$slug`) aren't found automatically. They get prerendered because a page links to them and the crawler follows the link. A project page that nothing links to won't be built
- Code in a component runs in two places: in Node at build time, and in the browser. Anything that touches `window` or `localStorage` must only run in the browser (inside `useEffect`)
- Keep `verbatimModuleSyntax` off in `tsconfig.json`. The Start docs warn it can pull server code into the client bundle

## 2. Tooling: formatting, linting, type checking, tests (16 Oct 2026)

Four separate tools, each answering a different question. All run from the repo root; `npm run check` runs the four in order and stops at the first failure.

| Command                           | Tool                        | Question it answers                                                                                                                                                                    |
| --------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run format` / `format:check` | Prettier                    | Is the code laid out consistently? It rewrites whitespace, quotes, line breaks. Never changes behaviour. `--check` only reports, which is what CI will run                             |
| `npm run lint`                    | oxlint                      | Does the code contain patterns that are probably bugs (a hook called conditionally, a missing effect dependency, `any`, an import cycle)? Reads code, doesn't run it                   |
| `npm run typecheck`               | TypeScript (`tsc --noEmit`) | Do the types line up? `--noEmit` means check only: Vite does the actual compiling, and it strips types without checking them, so a build can succeed with type errors unless this runs |
| `npm test`                        | Vitest                      | Does the code do what it should? Runs `*.test.ts` files                                                                                                                                |

### Config files

| File                    | What it does                                                                                                                                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.prettierrc.json`      | Same as grid tracker: no semicolons, single quotes, 120 columns, LF line endings                                                                                                                                                                                          |
| `.prettierignore`       | Skips build output, the lockfile and `routeTree.gen.ts` (generated, so formatting it is pointless)                                                                                                                                                                        |
| `.oxlintrc.json`        | A trimmed copy of grid tracker's. `categories` switches on groups of rules (correctness = error, suspicious and perf = warn); `rules` adjusts individual ones. `--deny-warnings` in the script makes warnings fail too, so nothing piles up                               |
| `.editorconfig`         | Tells your editor the basics (2-space indent, LF, final newline) before Prettier ever runs                                                                                                                                                                                |
| `.gitattributes`        | `* text=auto eol=lf`: Git stores and checks out LF line endings. Without it, Git on Windows (`core.autocrlf=true`) converts to CRLF on checkout, which fights Prettier's `endOfLine: lf`. That's what the "LF will be replaced by CRLF" warnings on the first commit were |
| `site/vitest.config.ts` | Kept apart from `vite.config.ts` so tests don't load the TanStack Start plugin and its prerender step. Tests are plain functions for now; a browser-like environment (jsdom) gets added when we test components                                                           |

### Why lint and typecheck are both needed

They overlap less than it seems. `tsc` knows types but nothing about React's rules: calling a hook inside an `if` type-checks fine and breaks at runtime. oxlint knows those rules but does far less type analysis. oxlint is written in Rust and checks this repo in milliseconds, which is why grid tracker uses it over ESLint.

### First test

`site/src/utils/pageTitle/` holds a tiny pure function and its test side by side, following grid tracker's convention of keeping a module and its tests in one folder. Both routes now use it, so the "Page · Matthew Suttie" format lives in one place. Pure functions (input in, output out, nothing else touched) are the easiest thing to test, which is a good reason to push logic into them.

## 3. Design tokens, global CSS and the base layout (16 Oct 2026)

### Design tokens

`site/src/styles/tokens.css` is the single place the look is defined: colours, fonts, type sizes, spacing, radii, page width and motion timings, all as CSS custom properties on `:root`. Components never use raw values like `#0c0d0f` or `24px`; they use `var(--bg)` or `var(--space-5)`. Changing the feel of the site means editing this one file.

Tokens come in two layers:

- **Raw scales** from Radix Colors (`--slate-1` … `--slate-12`, `--teal-1` … `--teal-12`). Each scale has 12 steps with fixed jobs: 1–2 backgrounds, 3–5 component fills, 6–8 borders, 9–10 solid colour, 11–12 text. That's why picking `--teal-11` for text is a safe contrast choice
- **Semantic tokens** that say what a colour is _for_: `--surface-1`, `--border`, `--text-muted`, `--accent`. Components only use these. A light theme later is a second block of semantic values pointing at the light Radix scales; no component changes

The Radix dark files only define their variables under `.dark`, which is why `<html>` has `className="dark"`.

### How CSS gets into the page

TanStack Start handles CSS imports like Vite does, plus it knows which CSS each route needs when prerendering:

- `import '../styles/global.css'` in `__root.tsx`: a side-effect import, so it applies everywhere. It pulls in the fonts, the tokens and a small reset
- `import styles from './SiteHeader.module.css'`: a **CSS Module**. Class names are rewritten to be unique (`.brand` becomes something like `_brand_1x2y3`), so two components can both have a `.bar` class without clashing. You use them as `className={styles.bar}`
- At build time all of it is bundled into one stylesheet, and the prerendered HTML links it in `<head>`, so the page is styled before any JavaScript runs

### Fonts

`@fontsource-variable/inter` and `/jetbrains-mono` ship the font files in the npm package, so the site serves its own fonts instead of calling Google Fonts. That's faster, works offline, and keeps a future Content Security Policy simple. The build outputs a file per character set (latin, cyrillic, greek…), but each is tagged with a `unicode-range`, so a browser only downloads the ones it needs: for English, just the latin file.

### Content kept separate from layout

`site/src/content/site.ts` holds the name, role, nav items and profile links. The header and footer just loop over it. Adding a nav item or changing a link is a content edit. The nav's `to` is typed from the generated route tree (`FileRouteTypes['to']`), so a link to a page that doesn't exist fails the type check.

### The layout

| Component                      | Job                                                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `components/layout/Container`  | Centres content and caps its width at `--page-width`, with side padding (`--page-gutter`)                        |
| `components/layout/SiteHeader` | Logo and name linking home; main nav                                                                             |
| `components/layout/SiteFooter` | Small logo, name, profile links                                                                                  |
| `components/ui/Logo`           | The ChronoLogic mark as an inline SVG: one arc and seven rays, drawn from a list of coordinates                  |
| `components/ui/ExternalLink`   | An `<a>` that opens in a new tab with `rel="noopener noreferrer"`, which stops the new page controlling this one |

`__root.tsx` now wraps every page in header, `<main>` and footer, so pages only render their own content.

### Two fixes along the way

- **Array index as a React key.** oxlint flagged `key={index}` in `Logo`. React uses keys to match list items between renders; an index breaks that if items are reordered. Here the list never changes so it was harmless, but each ray has a natural unique key (its end point), so we use that
- **The crawler followed `/#projects`.** The prerenderer treated the nav's hash link as a separate page and rendered the home page twice. A `filter` in `vite.config.ts` now skips any path with a `#`

## 4. The hero: animated dial, grid and mouse glow (16 Oct 2026)

### Hero content

`site/src/content/home.ts` holds the eyebrow, headline, intro and the main button. `Hero` reads it, so rewording the hero is a content edit.

### The dial: CSS animation driven by custom properties

`components/ui/Logo/mark.ts` holds the logo's geometry (the arc path and the seven rays) so `Logo` (static, in the header) and `Dial` (animated, in the hero) draw the same shape from one source.

The sweep is pure CSS, no JavaScript:

- Each ray gets `--step` (0–6) as an inline custom property
- They all run the same 7-second `sweep` keyframes, but each one's `animation-delay` is `--step × 1s`. So ray 0 flashes at 0s, ray 1 at 1s, and so on: a hand sweeping round. `--sweep-duration` controls the speed in one place
- `animation-fill-mode: both` holds each ray at its first keyframe (dim) during its delay, so nothing flashes on load
- Under `prefers-reduced-motion: reduce` the animation is switched off and each ray shows its resting opacity, matching the static logo

CSS animations run on the browser's compositor without React re-rendering, and they work from the prerendered HTML before any JavaScript loads.

### Grid and glow: two layers and a mask

The hero has two empty `<div>`s behind its content (`z-index: -1` inside a section with `isolation: isolate`, so "behind" means behind the hero content, not behind the page):

1. **`.grid`**: lines drawn with two `linear-gradient`s (one horizontal, one vertical) repeated every 48px. A radial `mask-image` fades it out towards the edges
2. **`.glow`**: the same grid, in teal, with a faint teal fill. Its mask is _two_ gradients combined with `mask-composite: intersect`: a 220px circle at the pointer, and the same edge fade. So it only shows where both allow, which keeps the glow inside the faded grid area

Both layers share `--grid-size` and `background-position`, so the teal lines sit exactly on top of the grey ones. The glow looks like light coming through the lines, not a separate shape.

### Tracking the pointer without re-rendering React

`hooks/usePointerTracking/` writes the pointer position as CSS custom properties (`--pointer-x`, `--pointer-y`) straight onto the hero element, plus `data-pointer="inside"` while the mouse is over it. CSS does the rest.

Why not React state? `pointermove` fires many times a second. Putting the position in `useState` would re-render the hero on every move. Writing to the element's style changes only what CSS reads, so React doesn't re-render at all.

Details in the hook:

- **`useRef` + `useEffect`**: the ref gives the real DOM element, and the effect runs only in the browser, never during prerendering in Node, where there's no mouse or `window`
- **`requestAnimationFrame`**: at most one update per screen frame, dropping any extra events in between
- **`pointerType === 'mouse'`**: on touch screens there's no hover, so the glow would just jump to wherever you tapped. Touch devices see the plain grid
- **Cleanup**: the effect returns a function that removes the listeners and cancels any pending frame, so nothing leaks if the hero unmounts (e.g. navigating to About)
- The maths (`pointerOffset`) is a separate pure function with its own test, the same pattern as `pageTitle`
